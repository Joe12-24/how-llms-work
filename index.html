大模型，只做一件事：猜下一个词

ChatGPT 们看起来无所不知，内核却简单得惊人：给它一串词，它算出下一个词最可能是什么，拼上去，再猜下一个。训练、推理、Agent 三幕，全是这一件事的不同侧面。

全站只用两个例子：「猫 吃 鱼」讲训练与推理；「查明天上海天气」讲 Agent。带虚线下划的词都可以点开看人话解释。

先亲手玩一下：点一次，长出一个词

今天天气

模型心里在想：接「真」有 41% 把握，接「很」有 23%，接「不」有 9%……

每点一次，它只猜一个词，然后把新词拼回句子、再猜下一个——这就叫逐词往外蹦 自回归。

第一幕 · 训练：它是怎么「学会」接龙的？

训练 = 让一台一开始满嘴胡话的机器，做几亿道「猜下一个词」的填空题，每错一次就微调自己一点点。用步进器慢慢看：

动手拧一下：步子迈多大？步长 学习率

每次改参数，步子迈多大最合适？拖动滑杆，看右边错题分数 Loss曲线怎么变。这是训练里最要命的一个设置。

教学简化曲线：真实训练同理，只是轮次以亿计。

纵轴 = 错题分数 Loss（越低越好）· 横轴 = 训练轮次。曲线由左侧滑杆实时算出，不是图片。

别怕，再手算一次：只有 1 个旋钮时，一轮训练长什么样？

真实模型有上千亿个旋钮，原理和 1 个旋钮时一模一样。点「一步步算」逐格看：

1
预测 = 输入 × 旋钮
2 × 0.5 = 1.0

输入 2，旋钮（权重 w）现在是 0.5，模型猜出 1.0。

2
对答案，算错多少
真实 = 3，Loss = (1−3)² = 4

正确答案是 3，猜错了，错题分数 Loss = 4。

3
这个旋钮该往哪拧？
梯度 = −8（负 = 该调大）

方向盘 梯度告诉每个旋钮：往哪拧、拧多少，错就能变小。

4
拧一下（步长 0.1）
w = 0.5 − 0.1×(−8) = 1.3

新预测 = 2×1.3 = 2.6，已经很接近 3 了。再来几轮就几乎不差。

≈ 10 万亿词

训练数据量级：近乎整个公开互联网的文本，都被切成填空题喂给它。

≈ 千亿个旋钮

参数量级：GPT 级别模型有上千亿个可调旋钮，每个都要算梯度、被拧动。

数万块 GPU · 数月

算力量级：一次完整训练烧掉的电费以千万美元计——这就是它「贵」的来源。

本页所有数字均为教学简化值；真实训练是「亿级参数 × 亿万次重复」同一套动作。

给开发者的落点 · 训练这一幕和你有什么关系？

  • 你几乎不会从零训练大模型——成本是千万美元级。你真正会做的是三件事：直接调 API、在现成模型上小班补课 微调 Fine-tuning、写好提示词。
  • 成本花在哪：从零训 = 数据 + GPU 集群 + 电费；微调便宜几个数量级；调 API 是按量付费，零前期投入。
  • 所以面试和工作中说的「做大模型」，99% 指的是用模型，不是造模型。造模型是少数大厂的核心团队在做的事。

第二幕 · 推理：训好的模型，怎么算出「鱼」？

还是那只猫。模型已经训好，现在给它「猫 吃」，看它的大脑内部一步步算出下一个词是「鱼」。点矩阵里的任意一格，可以看那一格是怎么来的。

亲手调：回答的「疯癫程度」随机度 温度 Temperature

第 5 步「挑词」不是永远挑第一名。温度越低越保守、越爱选最高分；越高越敢选冷门词——写代码要低温，写诗可以高温。

为什么「吃」必须回头看「猫」？

单独看「吃」，下一个词可能是饭、面、药……是「猫」在吃，才轮到「鱼」登场。互相打量 注意力 Attention就是让每个词在做决定前，先按重要程度把其他词「看一遍」：主语是谁、和自己有没有关系。

这也是 Transformer 架构的核心发明——2017 年那篇著名论文标题就叫 Attention Is All You Need（你只需要注意力）。

左边步进器第 3 步的热力图里，点任意一格看看具体的「看」法。

给开发者的落点 · 推理这一幕和你有什么关系？

  • 为什么按 token 收费、按 token 限长：模型每生成 1 个词就要把整个网络算一遍，算力正比于词数。输入 + 输出的 token 数，就是账单和延迟的来源。
  • 为什么要流式输出：逐词生成天然是一个一个往外蹦的，等全部生成完再返回，用户要盯着白屏好几秒——所以前端用流式（SSE / WebSocket）接一个渲染一个。
  • 备忘录 KV Cache：已经算过的词的结果会被缓存复用，不必每步从头重算——这是推理能跑得动的关键优化，也是显存吃紧的原因。

第三幕 · Agent：会自己干活的模型

场景：你说「查一下明天上海的天气，下雨就提醒我带伞」。模型本身不会查天气——它会指挥你的后端代码去查。所谓 Agent，就是围着模型写的一个循环：

上下文：0 / 200,000 tokens

🌦 天气工具 get_weather()

你的后端代码：真的去调天气 API。

状态：待命

⏰ 提醒工具 set_reminder()

你的后端代码：真的去建一条提醒。

状态：待命

左边颜色图例：紫 = 系统设定 · 蓝 = 用户 · 绿 = 模型 · 橙 = 工具结果。这四种消息拼成的列表，就是每轮发给模型的全部内容。

⚠ 翻车点 1：上下文塞满

聊太久、工具结果太长，列表超过模型的记忆上限就装不下了。对应技巧：把旧对话压缩成摘要、截断不重要的部分，只留关键信息。

⚠ 翻车点 2：工具报错

天气 API 超时、参数写错，后端调用失败。对应技巧：别吞掉错误——把报错信息也写回上下文，模型读到后会自己换个方式重试。

⚠ 翻车点 3：死循环

模型反复调同一个工具、原地打转，烧的全是你的钱。对应技巧：在你的循环里写死最大轮数（比如 10 轮），超了就强制停下并汇报。

一句话祛魅 · 先查资料再答题 RAG

没有黑魔法：先用你的代码去文档库里搜出相关段落，把段落拼进上下文，再让模型照着答。模型没变聪明，只是答题时手边多了你递的资料。

一句话祛魅 · 按格式点单 Function Calling

模型按你们事先约定的 JSON 格式，「说出」想调哪个函数、参数是什么。真正执行的永远是你的后端代码——模型只有建议权，没有执行权。

给开发者的落点 · Agent 的后端，就是你写的 while 循环

  • 后端负责：维护上下文列表、执行工具、控制最大轮数、把结果写回——全是普通后端活儿。
  • 前端负责：流式渲染模型逐词输出、展示「正在调用天气工具…」这类工具状态、渲染最终答复。
# Agent 的本质：一个 while 循环（伪代码）
messages = [system_prompt, user_msg]   # 上下文列表
for step in range(MAX_STEPS):          # 最大轮数，防死循环
    reply = llm.chat(messages)         # 1. 调模型
    if reply.tool_call:                # 2. 模型想调工具？
        result = run_tool(reply.tool_call)  # 3. 你的后端真去执行
        messages.append(result)        # 4. 结果写回上下文
    else:
        return reply.text              # 5. 没工具要调 = 最终答复

三幕一句话总结：训练 = 做亿道填空题、错一次拧一次旋钮；推理 = 训好的模型逐词往外蹦答案；Agent = 你的代码围着模型写了个循环，让它能指挥工具干活。你日常开发打交道的，主要是第二、三幕。
